# 日志、Tiger 与静态诊断

## 将报告绑定到输入

记录日志时间、游戏/Mod 版本和候选 hash。使用校验器时再记录工具版本、完整参数、工作目录、descriptor、依赖根与实际加载顺序。来源不明的报告仍可分析，但不能将其缺陷直接归给当前候选。

按语法、字段/数据库、scope、缺失引用、版本/依赖分组。诊断级别用于排序，不证明对应运行故障已发生。区分工具执行失败、脚本发现问题与缺乏运行证据。

## Tiger 或其他静态校验器

只有在用户环境确实提供 Tiger 或其他校验器时才执行。先从项目/技能目录的 README 或用户提供的信息取得当前可执行文件路径；不要复制其他作者机器上的绝对路径，也不要因文档提到工具就假定本机已安装。

首次使用或工具版本变化时：

1. 确认可执行文件真实存在，并读取其版本或帮助输出。
2. 确认目标 descriptor、Mod 根目录、依赖和当前候选身份。
3. 先运行一次基线检查，保存完整参数、退出码、stdout/stderr 和原始报告。
4. 将 error、warning、tips 等级别分组，结合对应源码和调用链判断；工具级别不等于游戏运行后果。
5. 汇总一轮相关问题后再修复，避免为每条提示重复启动重型校验器。
6. 修改后按同一输入边界重跑，比较新增、消失和仍存在的问题；保留未解决基线。

若没有工具或路径未确认，标记 NOT RUN / BLOCKED，继续进行可做的源码审查；不得默默下载、安装或运行未获授权的程序。不要把 Tiger 结果称为引擎语义验证、实际加载或游戏验收。

## 从现象到可验证修复

每个相关问题保留原文/位置、受影响调用链、根因假设、修复与判据。对照旧基线列新增、已解决和保留项；不要为小修复清空无关警告，也不要抹掉尚未解决的旧失败。

有已接入的 Tiger 或其他校验器时，先读真实版本与 help，再按其当前参数运行。没有工具就标 NOT RUN，继续源码分析；不复制作者机器路径、不默默下载工具，也不把查询适配器当已有执行器。

相关修改完成后运行所需检查；只有新变更、失败或未解决疑问才扩大或重复。保存参数向量、工作目录、退出码、stdout/stderr 与输入身份；解析失败保留原报告，并标 INCONCLUSIVE。

## 结果等级必须分开

静态检查、部署回读、实际加载、热加载、渲染和场景结果独立记录。无报错、给出复现步骤或工具已安装，都不等于玩法通过。静态工具未发现问题只能说明其覆盖范围内没有报告问题。
