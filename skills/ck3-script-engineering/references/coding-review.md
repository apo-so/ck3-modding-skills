# 文件、参数、兼容与重复求值检查

## 文件与定义

修改前确认实际数据库和目标 owner；保留 BOM、换行、稳定键名及未改内容。新建文件参考当前 schema 和同类加载路径，不凭文件夹名字推断子目录语义。CK3 常见文件归属包括 events、common/decisions、common/scripted_triggers、common/scripted_effects、common/on_action、gui 和 localization；具体二级目录仍须按目标数据库核验。为自定义标识符使用稳定的 Mod 前缀，脚本标识符通常采用 ASCII 字符，中文放在本地化值中。不要为了格式统一而重排无关内容。

## 参数与值的寿命

把调用点的参数代入被调用定义，检查替换位置、scope 及期待类型，特别是 trigger/effect/value 表达式不能互换。参数替换只改变展开文本，不会自动冻结动作发生时的数值。

需要历史结果时确认求值时刻和保存 owner，再决定是否存快照；正确的动态读取不必为了复用而新增持久状态。每个变量、flag、列表和保存 scope 都应能说明谁写入、谁读取、由谁清理，以及延迟事件发生时对象是否仍然有效。

## Scope 与代码结构

- 写代码前标明当前 scope、目标 scope、actor、recipient、root、this、prev 和已保存 scope 的含义；root 不自动等于玩家。
- 区分 trigger 与 effect；limit、is_shown、is_valid 等条件位置不能混入状态变更。
- 共享条件、状态变更和数值计算可分别抽取为 scripted_trigger、scripted_effect、script_value；抽取本身不等于缓存，也不能隐藏必要的 scope 前提。
- 检查每个 scope 跳转的合法性和中间对象是否可能不存在；多对一/一对多关系不能仅凭看似顺畅的点链推断。
- 对延迟事件、on_action 和跨事件链，检查保存 scope 的类型、寿命、覆盖和清理。

## 加载与兼容性

不要把兼容性缩减为“两个 Mod 是否修改同名文件”。至少检查：

1. **文件冲突**：多个 Mod 替换同一路径，实际加载顺序决定文件来源。
2. **定义键冲突**：不同文件声明同一数据库键或脚本对象。
3. **语义冲突**：没有同键覆盖，但双方对状态、参数、前置条件或副作用的假设不一致。
4. **调用方/被调用方冲突**：一个 Mod 改变被调用定义，另一个 Mod 仍按旧语义调用。
5. **加载顺序依赖**：注册、覆盖或执行次序改变结果。
6. **GUI 冲突**：模板、widget、blockoverride、datacontext 或控件 owner 重叠。
7. **本地化冲突**：同一键的覆盖改变显示含义，或掩盖实际脚本问题。

优先新增独立文件和新定义，慎用整文件覆盖；能通过稳定 hook 扩展时，不复制整份原版文件。不要依赖同 ID 事件重定义实现补丁，必须查明目标版本的注册/覆盖行为。

扩展已有原版 on_action 时，先检查其原生 effect 和执行上下文。若原版入口已经有 effect，不要简单再写一个同名 effect；应核对目标版本支持的 on_actions 扩展/桥接方式，并检查是否重复触发。不要将某个常见写法当成所有 on_action 的无条件模板。

可选跨 Mod 集成应定义清晰、稳定的接口，并核对缺失引用时的真实行为。不要把缺失 scripted trigger/effect/modifier 当作控制流程；缺失引用可能产生误判、日志噪声或启动风险。

## 性能与重复求值

先确认执行频率、遍历集合与已观察成本，再优化查询。缩小查询应仍覆盖用户要求的目标，不能靠新增玩法资格消除负担。提取成 scripted_trigger 或 script_value 表示复用，不自动形成缓存；缓存必须说明保存、刷新与失效条件。没有同条件对照不宣称性能提升。

对 GUI 可见性、有效性检查和 AI 权重中的 any_/every_ 遍历尤其谨慎：先做低成本筛选，避免高频全局扫描。只有在测量或明确调用频率支持时才进行缓存或结构性优化。

## 修改与复核

每项审查意见记录：文件/定义、调用链、问题类型、证据、最小修复、可能影响的调用方、需要的静态检查和游戏内场景。修复后复查同一失败路径，并保留未解决项；不要把“语法通过”写成“机制通过”。
